# How the four Top-k methods use GPU threads

A **thread** works on a few scores. A **block** is a team of threads that can share fast memory and wait for one another. All methods return the highest scores first, using the smaller token ID to break a tie; the [shared benchmark](../benchmarks/run_shared_comparison.py) runs them on one ordered CUDA stream and uses the same [sampler](../src/sampler.cu).

| Method                                                 | What threads do                                                                                                                                                                                                                          | Why it may be fast or slow                                                                               |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| [Full sort](../src/full_sort.cu)                       | Threads copy scores and token IDs into GPU memory, adding empty slots to make sorting easier. At each step, a thread compares one pair and swaps it if needed; all blocks finish before the next GPU step starts.                        | It sorts **all** scores even when `k` is small, so many steps and memory reads and writes can be costly. |
| [Hierarchical Top-k](../src/hierarchical_topk.cu)      | In each group of 256 scores, 256 threads in one block sort the scores **together**, waiting after each comparison step. Each group keeps its best `k`, then blocks merge neighboring lists in rounds like a tree until one list remains. | Keeping only `k` per group saves work, but each merge round reads and writes lists again.                |
| [Radix Top-k](../src/radix_topk.cu)                    | Threads read a few scores each and count their score bits in shared memory, repeating four times to find the Top-k cutoff. Threads mark the winners; GPU library code gives each winner a position and sorts the final `k` values.       | It sorts only the winners, but rereads all scores and needs extra temporary memory and GPU steps.        |
| [PyTorch adapter](../benchmarks/torch_topk_adapter.py) | PyTorch decides what each `topk` thread and block does internally; that code is outside this repository. More GPU steps find tied scores, choose the smaller token IDs, and put the winners in order.                                    | Built-in Top-k may be fast, but fixing ties reads all scores and needs extra memory and GPU steps.       |

The sampler gives **one block to each row**: threads compute probabilities for different scores, add them together, and build a running probability total. Threads wait for one another inside the block; separate GPU steps run in order on the stream.

## What the saved timings show

Only [full-sort selection timing](../results/full-sort-20261110T024826218088Z/summary.csv) is saved for a selector. On a P100 with 50,257 scores per row, the `01_everyday` group took **0.487 ms** for `B=1, k=1` and **0.485 ms** for `B=1, k=100` (medians across 32 windows): `k` barely matters because all scores are sorted. At `B=32, k=100`, one window took **7.709 ms**; 32 times more rows took about 16 times longer, consistent with blocks working in parallel.

A separate [sampler-only test](../results/sampler_01_everyday.csv) measured **12.608 µs** at `B=1, k=100`; it did not time selection. **No saved run compares all four selectors or times selection plus sampling together.** Their relative speed and full-pipeline speed are therefore still unknown, and separate timings should not be added together to claim a pipeline result.
